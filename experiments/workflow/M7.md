# M7 — Measure the 0.5.0 perception tools

Started 2026-11-07, after the maintainer published `releases/0.5.0`
(`b4eb30ba36b3c525d76dd96129c28a52c5ce6d7a`, Package Manager asset
`rhinomcp-0.5.0-rh8_17-any.yak`). The release's premise is that agents which
ground themselves (`get_context`) and read what a capture shows
(`capture_viewport` metadata) are flagged less often by the M1 flaw report. This
milestone measures that on fresh runs instead of assuming it.

## Protocol, declared before any run

Everything in this section was written and committed before the first 0.5.0
modeling session. Nothing below is tuned after seeing results.

- Rhino 8 on the supervised host with RhinoMCP 0.5.0 from the Package Manager

### Why the sealed bank is not spent

The milestone text says to re-run the held-out family bank. The three sealed,
unopened families cannot measure this release:

- `instance-block-reuse-v1` and `mesh-connectivity-repair-v1` are specifications
  without calibrated adapters, and the 0.5.0 catalog has no instance-definition
  or mesh-repair commands (instances were deferred from 0.5.0). Any run would
  record unmet capability, not perception behavior.
- `gh-pattern-filter-v1` runs through the Grasshopper gateway, which exposes
  `gh_*` tools only; neither perception tool exists there.

Spending them would exhaust the bank without an observation about the release,
and closing them would require sealing three replacements. They stay sealed.
Instead the two held-out families that already have plain 0.4.1 runs, joining
and projection (spent and closed in M3b), are re-run as discovery families. They
are not claimed unseen; their M3b baseline arms are the like-for-like 0.4.1 rate.
This is recorded as a finding against the M7 wording, not as a silent change.

### Trace facts

Computed by `m7.py` from `modeler/events.jsonl` without changing the M1
classifier (`flaws.py`, `audit.py` are untouched):

- **Grounded**: a completed `get_context` call precedes the run's first call to
  any tool outside the non-edit set (reads, discovery, selection, camera, and
  script-documentation tools), or the run makes no edit call at all.
- **Captured**: at least one completed, non-failed `capture_viewport` call.
- **Verified**: captured, and the metadata text block of the last capture is
  reflected afterwards in an agent message or a tool argument: a metadata key
  name, a bounding-box or camera number (decimal or two or more digits), or an
  object count together with its noun. Bare small integers do not count. A
  capture followed by acceptance with no such use counts as not verified. A
  supervisor review (`m7-review.json`) may override the heuristic per run, only
  with the trace hash, a reason and a quoted excerpt; every run with a capture is
  reviewed by hand and the review recorded.

### Flagged run

A run is flagged when its M1 report holds at least one finding with confidence
`observed` or `reviewed`, excluding `failed_call` findings caused by the gateway
(`host_execution_refusal`, `host_component_refusal`, `gateway_scope`), as keep
rule v2 requires. Observations (discovery) and candidates (retries, recovery
loops, script fallbacks) do not flag a run; they are reported beside it.

### 0.4.1 baseline

`m7-baseline-runs.json` lists the 25 plain Codex runs on released 0.4.1: the nine
M0b observations (`release-041-runs.json`) and the sixteen M3b baseline arms
(`m3b-cycle1-runs.json`, `m3b-cycle2-runs.json`, cohorts ending `-baseline`).
Candidate arms carried description changes and are excluded; Claude runs are a
different agent and are excluded. Classified with today's `flaws.py`, which
post-dates M3b's cause corrections, 6 of 25 are flagged (24%): one completion
contradiction (panel, native), one redundant read (panel), four missing-layer
failed calls (joining and projection). The M0b nine alone: 1 of 9 (11%).
In 0.4.1 `get_context` did not exist, so every baseline run is "not grounded";
one baseline run captured a viewport and did not use its metadata.

### Reading the result

Compare the overall 0.5.0 rate with 24% (all 25) and 11% (M0b nine), then the
grounded-and-verified group against the other three groups. With 20 full-catalog
runs, a group under five runs cannot be separated from noise and is said so.
Repeats on the same tasks are descriptive evidence, not a causal estimate.

Four runs (`93c63146` closed-network, two-components and vertical projection;
`fbe91c82` vertical projection) are flagged only because `get_objects` was called
with `layer_filter` set to the task's target layer (`Joined`, `Results`) before that
layer existed, and 0.5.0 answers `not_found: Layer 'Joined' not found` with the
guidance line "Call get_document_summary to list existing layers, or create_layer
to make it first." On 0.4.1 `get_objects` had no layer filter, so this probe could
not happen; agents there listed everything and filtered themselves. Whether a
read-only probe of an absent layer should be an error is a product question, not
a detector question: the M1 classifier labels it correctly as a failed call with a
missing-layer cause, and keep rule v2 does not exclude it. Recorded as follow-up (1)
in the brief; nothing changed here.

Three runs fail `update_object_attributes` on an absent layer, as 4 of the 10
0.4.1 joining and projection baseline arms did. In `fbe91c82` two-components the
agent received the guidance line at `item_13`, repeated the same call at `item_14`
and again at `item_25` after a second `get_context`, and only then called
`create_layer` (`item_26`). The coded error with a guidance line did not shorten
that loop; M3c target 3 (listing existing layer paths in the error) remains open.

Gateway refusals, not flags: 11 execution-tool attempts in the 8 joining and
projection runs (0.4.1: 9 in 10), all for `_Join` or a scripted join after
`search_rhinoscript_functions("join curves")`. The missing typed join operation is
the standing unmet capability from M3b.

### Reading the comparison

- Overall, 0.5.0 is flagged slightly more often (7/25 against 6/25); the difference
  is four runs of the new probe class on tasks whose families are the hardest in
  the bank. Removing those four post hoc gives 3/20 full-catalog runs (15%) against
  5/20 (25%) on 0.4.1. That sensitivity figure is reported for context only; the
  pre-declared rule stands.
- Grounding is adopted (18/20) and costs about two calls per run (36 `get_context`
  calls; agents call it at the start and again before accepting). Its payload
  (units, tolerance, layer count, object count, empty bounding box) was returned to
  agents that then still assigned objects to layers that did not exist, so the
  snapshot did not prevent the one friction class seen.
- Verification was never attempted. On this bank every requirement is numeric and
  agents check it with `analyze_objects`, `get_objects` and `get_object_attributes`;
  nothing in the tasks or the role prompt asks for a look, and the saved-file
  evaluators cannot reward one. The release's "read what the capture shows" premise
  needs tasks where a picture answers a question numbers do not (placement in a
  prepared scene, occlusion, visual composition) before it can be measured.
- Task success: 25/25 on 0.5.0 against 24/25 on 0.4.1 (the M0b panel). The 0.5.0
  panel run used the same seven-call pattern as the failing 0.4.1 run; one pass is
  a single observation, not an improvement claim.
- Groups under five runs: "verified only", "grounded and verified" and "verified"
  have zero runs; "neither" and "not grounded" are the five native runs plus two
  inspection runs, which never flag on either version. No causal reading is
  available from this split.

### Detector notes

The M1 classifier was not changed. Two gaps for a separate ticket:

1. `flaws.READS` does not know `get_context`, `get_document_summary`,
   `measure_objects` or `select_objects`. They are treated as mutations, so each
   acts as a barrier that can hide a redundant read on either side of it. Checked
   against these traces: widening the read set would add exactly one
   `redundant_read` flag, `select_objects` repeated with identical arguments and
   response in `workflow-baseline-20261107-201636-67a6ac14-edit_existing-v1`
   (`item_9`, `item_11`), which would make the 0.5.0 count 8/25 (32%) and the
   grounded group 8/18. The pre-declared rule uses today's classifier unchanged,
   so the table above stands; the gap will matter more as agents ground more.
2. The new coded error prefix `not_found:` matches the existing `layer.*not found`
   cause pattern; object errors of the form `not_found: Object ... not found` also
   match. No misfire on the new tools was observed in these 25 traces.
