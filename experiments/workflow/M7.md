# M7 — Measure the 0.5.0 perception tools

Started 2026-11-07, after the maintainer published `releases/0.5.0`
(`b4eb30ba36b3c525d76dd96129c28a52c5ce6d7a`, Package Manager asset
`rhinomcp-0.5.0-rh8_17-any.yak`). The release's premise is that agents which
ground themselves (`get_context`) and read what a capture shows
(`capture_viewport` metadata) are flagged less often by the M1 flaw report. This
milestone measures that on fresh runs instead of assuming it.

## Protocol, declared before any run

Everything in this section was written and committed before the first 0.5.0
modeling session. Nothing below is tuned after seeing results.

### Environment

- Rhino 8 on the supervised host with RhinoMCP 0.5.0 from the Package Manager
  and `mcpstart` issued; one fresh, unsaved, empty document.
- Server under test: `server/` of this checkout at the release commit, installed
  editable in `server/.venv` (reports 0.5.0). `describe_capabilities` must report
  `version` and `server_version` 0.5.0 with no `update_advice`.
- `select_release("releases/0.5.0", identity, "0.5.0")` records the loaded
  identity (MVID, SHA-256) in a selection journal; `current-baseline.json` then
  moves to 0.5.0 and the 0.4.1 entry goes to `baseline-history.json`.

### Runs

Same agent, budgets and tasks as the 0.4.1 runs: Codex `gpt-5.6-terra`, medium
reasoning, fresh session per attempt, no guidance or description candidate, the
host gateway refusing and recording the three execution tools. Every attempt is
retained; nothing is rerun to pass. Repeats are declared here, not added later.

| Suite | Catalog | Attempts | Runs | 0.4.1 comparison |
| --- | --- | ---: | ---: | --- |
| `release-pilot.json` (5 native families) | 14-tool native subset | 1 | 5 | M0b native runs (5) |
| `m2-pilot.json` (4 scene families) | full production catalog | 3 | 12 | M0b scene runs (4) and M3b baseline arms for editing and assembly (6) |
| `m7-heldout.json` (joining, projection; 4 tasks) | full production catalog | 2 | 8 | M3b baseline arms (10) |

The native subset does not expose `get_context` or `capture_viewport`, so those
five runs measure the overall 0.5.0 rate only and fall in the "neither" group by
construction. The grounded/verified split is read within full-catalog runs.

### Why the sealed bank is not spent

The milestone text says to re-run the held-out family bank. The three sealed,
unopened families cannot measure this release:

- `instance-block-reuse-v1` and `mesh-connectivity-repair-v1` are specifications
  without calibrated adapters, and the 0.5.0 catalog has no instance-definition
  or mesh-repair commands (instances were deferred from 0.5.0). Any run would
  record unmet capability, not perception behavior.
- `gh-pattern-filter-v1` runs through the Grasshopper gateway, which exposes
  `gh_*` tools only; neither perception tool exists there.

Spending them would exhaust the bank without an observation about the release,
and closing them would require sealing three replacements. They stay sealed.
Instead the two held-out families that already have plain 0.4.1 runs, joining
and projection (spent and closed in M3b), are re-run as discovery families. They
are not claimed unseen; their M3b baseline arms are the like-for-like 0.4.1 rate.
This is recorded as a finding against the M7 wording, not as a silent change.

### Trace facts

Computed by `m7.py` from `modeler/events.jsonl` without changing the M1
classifier (`flaws.py`, `audit.py` are untouched):

- **Grounded**: a completed `get_context` call precedes the run's first call to
  any tool outside the non-edit set (reads, discovery, selection, camera, and
  script-documentation tools), or the run makes no edit call at all.
- **Captured**: at least one completed, non-failed `capture_viewport` call.
- **Verified**: captured, and the metadata text block of the last capture is
  reflected afterwards in an agent message or a tool argument: a metadata key
  name, a bounding-box or camera number (decimal or two or more digits), or an
  object count together with its noun. Bare small integers do not count. A
  capture followed by acceptance with no such use counts as not verified. A
  supervisor review (`m7-review.json`) may override the heuristic per run, only
  with the trace hash, a reason and a quoted excerpt; every run with a capture is
  reviewed by hand and the review recorded.

### Flagged run

A run is flagged when its M1 report holds at least one finding with confidence
`observed` or `reviewed`, excluding `failed_call` findings caused by the gateway
(`host_execution_refusal`, `host_component_refusal`, `gateway_scope`), as keep
rule v2 requires. Observations (discovery) and candidates (retries, recovery
loops, script fallbacks) do not flag a run; they are reported beside it.

### 0.4.1 baseline

`m7-baseline-runs.json` lists the 25 plain Codex runs on released 0.4.1: the nine
M0b observations (`release-041-runs.json`) and the sixteen M3b baseline arms
(`m3b-cycle1-runs.json`, `m3b-cycle2-runs.json`, cohorts ending `-baseline`).
Candidate arms carried description changes and are excluded; Claude runs are a
different agent and are excluded. Classified with today's `flaws.py`, which
post-dates M3b's cause corrections, 6 of 25 are flagged (24%): one completion
contradiction (panel, native), one redundant read (panel), four missing-layer
failed calls (joining and projection). The M0b nine alone: 1 of 9 (11%).
In 0.4.1 `get_context` did not exist, so every baseline run is "not grounded";
one baseline run captured a viewport and did not use its metadata.

### Reading the result

Compare the overall 0.5.0 rate with 24% (all 25) and 11% (M0b nine), then the
grounded-and-verified group against the other three groups. With 20 full-catalog
runs, a group under five runs cannot be separated from noise and is said so.
Repeats on the same tasks are descriptive evidence, not a causal estimate.
